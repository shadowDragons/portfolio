# 什么是 MongoDB

MongoDB 是一种文档型数据库。它不用传统的表格来存数据，而是把数据保存成一条条类似 JSON 的文档。下面会讲清它到底是什么、和关系型数据库差在哪、内部靠什么保证性能和高可用，以及它适合放在哪些场景里。

![以 MongoDB 为中心节点、辐射四个主题分支的手绘放射图](/blog/什么是-mongodb-文档型数据库的核心机制-高可用与适用场景/scene-1-1.png)

## MongoDB 是什么：文档与集合

MongoDB 常被归到 NoSQL 数据库这个大类。NoSQL 不是“没有 SQL”，而是“不只是 SQL”，指的是不把数据强行塞进固定表结构的一类数据库。

它的核心单位叫文档。你可以把它想成一张写满键值对的单据：字段能嵌套，也能放数组。

把多个文档放在一起，就构成一个集合。集合大致相当于关系数据库里的表。

![文档由键值对字段构成，多个文档组成集合的示意图](/blog/什么是-mongodb-文档型数据库的核心机制-高可用与适用场景/scene-2-2.png)

## 和关系型数据库差在哪

这里最关键的区别是结构。关系型数据库里，表要先定义好有哪些列，每一行的格式必须一致。

MongoDB 的文档不用提前定义字段。同一个集合里的两条数据，可以有完全不同的结构。

![关系型数据库固定列结构与 MongoDB 灵活字段结构的对比图](/blog/什么是-mongodb-文档型数据库的核心机制-高可用与适用场景/scene-3-3.png)

这带来一个直接好处：需求一变，你不用马上改表结构，直接往文档里加字段就行。

## 文档长什么样

假设你要存一个用户。关系型数据库可能要拆成用户表、地址表、订单表，再用外键关联。

在 MongoDB 里，你可以把地址和最近几笔订单，直接嵌套进同一个文档。一次查询就能把需要的数据整个取回来，省掉了多表连接。

![单个用户文档内嵌套地址与订单、一次查询取回整块数据的示意图](/blog/什么是-mongodb-文档型数据库的核心机制-高可用与适用场景/scene-4-4.png)

这种把相关数据放在一起的设计，解决的是读写效率问题。应用读一个用户详情，往往一次操作就够了，不用拼好几张表。

代价是同样的数据可能在多个文档里重复出现，更新时得同步改多处。所以它更适合读多写少、结构灵活的场景。

![从多表拼接查询走向单文档一次读取，并标注数据重复代价的示意图](/blog/什么是-mongodb-文档型数据库的核心机制-高可用与适用场景/scene-5-5.png)

## 高可用与扩展：副本集和分片

性能之外，大家最担心的是可靠性。MongoDB 用副本集解决高可用，也就是把同一份数据复制到多台机器上。

其中一台是主节点，负责接收写操作；其他是从节点，实时同步数据。主节点一旦宕机，从节点会自动选出新的主节点，服务很快恢复，不用人工干预。多一个从节点，也就等于多一份数据副本。

![副本集主从数据复制、节点宕机与自动故障切换的分镜示意图](/blog/什么是-mongodb-文档型数据库的核心机制-高可用与适用场景/scene-6-6.png)

数据大到一台机器存不下时，就用分片。分片的意思是，按某个规则把数据切开，分散到多台机器上，比如按用户 ID 的区间来分。

查询请求会被路由到对应的分片，压力就被摊开了。这套机制让 MongoDB 能靠加机器来提升容量，而不是只能换更强的单机。数据量继续涨，就继续增加分片机器。

![数据按规则分叉到多个分片机器、查询请求被路由的示意图](/blog/什么是-mongodb-文档型数据库的核心机制-高可用与适用场景/scene-7-7.png)

## 怎么把数据查出来

它的查询语法也是基于文档的。你可以写条件去匹配字段，还能直接匹配数组里的某个元素。

它同样支持索引。给常用字段建好索引后，查询不用扫全表，能直接从索引定位。这一点，和关系型数据库的思路是一致的。

![查询先按条件匹配字段或数组元素，再通过索引直接定位的流程图](/blog/什么是-mongodb-文档型数据库的核心机制-高可用与适用场景/scene-8-8.png)

索引字段选得准，查询才快得起来。

## 适合用在哪里

比较典型的有三类：

- 内容和用户数据变化频繁的应用，比如电商商品、社交动态，字段经常增减。
- 物联网和日志系统，会有大量设备数据高速写入。
- 实时性要求高的应用，需要快速读回一整块相关数据。

![三类适用场景三宫格：字段多变、物联网日志、高实时读回](/blog/什么是-mongodb-文档型数据库的核心机制-高可用与适用场景/scene-9-9.png)

这三类场景有个共同点：数据模型不那么规整。

## 不适合什么

如果你的业务有复杂的多表关联查询，或者对跨表的事务一致性要求非常严格，比如银行转账，传统关系型数据库通常更稳妥。

![复杂多表关联与强一致需求更偏向传统关系型数据库的示意图](/blog/什么是-mongodb-文档型数据库的核心机制-高可用与适用场景/scene-10-10.png)

MongoDB 支持事务，但在强关联、强一致的需求上，关系型数据库积累得更成熟。

## 常见问题

**同一个集合里的文档结构必须一致吗？** 不需要。MongoDB 的文档不用提前定义字段，同一个集合里的两条数据可以有完全不同的结构。

**它支持索引吗？** 支持。给常用字段建好索引后，查询不用扫全表，能直接从索引定位。

**它支持事务吗？** 支持。但在强关联、强一致的需求上，关系型数据库积累得更成熟。

**主节点宕机了怎么办？** 其他从节点会自动选出新的主节点，服务很快恢复，不用人工干预。

**一台机器存不下全部数据怎么办？** 用分片：按某个规则把数据切开，分散到多台机器上，查询请求会被路由到对应的分片。

## 总结

MongoDB 的本质，是把数据从行和列换成了文档。用灵活的字段结构换取开发效率，用副本集换高可用，用分片换扩展能力。

抓住这三点，你就掌握了它和其他数据库最根本的差别，也能判断它该不该进入你的技术选型。
