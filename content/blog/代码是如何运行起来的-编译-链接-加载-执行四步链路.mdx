# 代码是如何运行起来的

你写下的几行文字，经过一连串翻译和搬运，最终会变成芯片里流动的电信号。本文从源代码讲起，依次走过编译、链接、加载、执行四个阶段，看清一段程序从文本变成动作的完整旅程。

![代码运行总览：从你写的几行文字，经编译、链接、加载、执行四个阶段，到芯片里流动的电信号](/blog/代码是如何运行起来的-编译-链接-加载-执行四步链路/scene-1-1.png)

## 什么是代码运行

代码运行，指的是人类可读的源文本被翻译成机器可执行的指令，再被操作系统送进内存，由 CPU 逐条执行的过程。

理解这条链路有一个直接收益：当程序出错时，你能分清是语法错误、链接错误，还是运行时崩溃，从而判断故障出在哪一环。

## 核心机制：四个阶段

一次完整的运行，大致要经过四步：

- 编译：把源码变成机器指令。
- 链接：把散落的模块拼成整体。
- 加载：把它送进内存并创建进程。
- 执行：让 CPU 逐条跑完。

接下来逐个展开。

## 编译：把人类能读的代码翻译成机器能执行的指令

起点是一个普通的文本文件，里面全是给人看的字符。可是 CPU 只认识电信号，它不认识 if，也不认识 print 这个单词。

![人类可读的文本代码（含 if、print）与 CPU 能识别的电信号/二进制左右对比](/blog/代码是如何运行起来的-编译-链接-加载-执行四步链路/scene-2-2.png)

翻译工作通常交给编译器。以 C 语言为例，编译器先做词法分析和语法分析，把代码拆成一个个记号，再检查结构对不对。

如果括号没配对、分号漏了，这一步就会直接报错，也就是常说的编译错误。这个阶段只检查形式，并不关心你的逻辑是否合理。

![编译器线性流程：词法分析、语法分析、结构检查、编译错误，并强调只检查形式](/blog/代码是如何运行起来的-编译-链接-加载-执行四步链路/scene-3-3.png)

通过检查后，编译器会做优化，把代码翻译成汇编语言，再进一步变成机器码。机器码就是一串二进制指令，CPU 能直接读懂它。

到这里，你得到的是一个目标文件，但它还不能直接运行。

![编译流程：源码经优化变成汇编语言，再变成机器码，最终得到还不能直接运行的目标文件](/blog/代码是如何运行起来的-编译-链接-加载-执行四步链路/scene-4-4.png)

## 链接：为什么目标文件还不能运行

原因在于，你的代码里常常会调用别人写好的函数，比如负责打印的 printf。这些函数躺在标准库里，还没被接进来。

于是链接器登场。它把你的目标文件和用到的库文件拼在一起，把每个函数调用的地址填对。

![桥接结构：代码调用 printf 等标准库函数却未接入的问题，由链接器登场解决](/blog/代码是如何运行起来的-编译-链接-加载-执行四步链路/scene-5-5.png)

如果某个函数只声明了却没实现，链接就会失败，这就是链接错误。链接成功后，你终于拿到了一个可执行文件，不过它躺在硬盘上，还是静止的。

![可执行文件由目标文件与库文件拼接组成，并填对每个函数调用的地址，旁注链接错误](/blog/代码是如何运行起来的-编译-链接-加载-执行四步链路/scene-6-6.png)

## 加载：从硬盘读进内存并创建进程

当你双击它或者敲下回车，操作系统会把文件从硬盘读进内存，为它分配地址空间，准备好堆和栈。

同时系统会创建一个进程，也就是这个程序正在运行的实例。同一份可执行文件可以同时跑出很多进程，彼此互不干扰。

![加载流程：双击或回车后文件从硬盘读进内存，分配含堆和栈的地址空间并创建进程](/blog/代码是如何运行起来的-编译-链接-加载-执行四步链路/scene-7-7.png)

## 执行：CPU 逐条取指令、译码、执行

CPU 里有个程序计数器，它始终指向下一条要执行的指令。CPU 一条一条地取指令、译码、执行，循环往复。

遇到函数调用就跳转，遇到条件判断就分叉，遇到循环就折返。你写的每一行逻辑，就是这样被拆成成千上万条微小动作，飞快地跑完。

![执行环形流程：取指令、译码、执行循环往复，中心是程序计数器指向下一条指令](/blog/代码是如何运行起来的-编译-链接-加载-执行四步链路/scene-8-8.png)

## 编译型、解释型与中间路线

Python、JavaScript 这类语言通常不走完整编译这条路。Python 代码会先被编译成字节码，然后由解释器一行一行地执行。

JavaScript 则常由浏览器引擎即时编译，边跑边优化那些反复执行的热点代码。

![Python 与 JavaScript 的语言卡片：字节码加逐行解释执行，以及浏览器引擎即时编译优化热点代码](/blog/代码是如何运行起来的-编译-链接-加载-执行四步链路/scene-9-9.png)

所以解释型语言启动快、写起来灵活，但通常比编译型语言慢一些。

Java 走的是中间路线，先编译成字节码，再由虚拟机在运行时翻译执行。

由此带来一个关键区别：编译型语言在运行前就把大部分翻译做完了，执行效率高；解释型把翻译放到运行时，灵活但多了开销。

![编译型、解释型与 Java 的矩阵比较：翻译时机、执行效率与灵活性](/blog/代码是如何运行起来的-编译-链接-加载-执行四步链路/scene-10-10.png)

## 实践场景：语言路线正在融合

现代很多语言其实在融合这两条路，即时编译技术会在程序运行时动态优化，兼顾启动速度和执行速度。

![桥接结构：编译型与解释型两条路跨越到即时编译，兼顾启动速度与执行速度](/blog/代码是如何运行起来的-编译-链接-加载-执行四步链路/scene-11-11.png)

## 限制与常见误区：越靠前的阶段，错误代价越小

把这套流程串起来，会发现一个有意思的规律：越靠前的阶段，错误越容易发现，代价也越小。编译期报错，改一行就好；运行期崩溃，可能已经上线了。

这也是为什么类型检查、静态分析这些工具越来越被重视，它们都在努力把问题往前推。

![层级结构：编译期、链接期、运行期自上而下，越往下发现越难、代价越大，顶部是类型检查与静态分析](/blog/代码是如何运行起来的-编译-链接-加载-执行四步链路/scene-12-12.png)

一个常见误区是把所有报错都当成同一类问题。实际上，编译错误、链接错误和运行时崩溃分别发生在不同阶段，定位方式和处理时机完全不同。

## 常见问题

### 编译错误和链接错误怎么区分？

编译错误发生在编译阶段，这一阶段检查的是形式与结构，例如括号没配对、分号漏了。链接错误发生在链接阶段，典型情况是某个函数只声明了却没实现。

### 为什么同一个可执行文件可以同时运行多次？

加载阶段会创建进程，也就是程序正在运行的实例。同一份可执行文件可以同时跑出很多进程，彼此互不干扰。

### 为什么解释型语言通常更慢？

编译型语言在运行前就把大部分翻译做完了，执行效率高；解释型把翻译放到运行时，灵活但多了开销。

## 总结

代码运行大致经过四步：编译把源码变成机器指令，链接把散落的模块拼成整体，加载把它送进内存并创建进程，执行让 CPU 逐条跑完。
